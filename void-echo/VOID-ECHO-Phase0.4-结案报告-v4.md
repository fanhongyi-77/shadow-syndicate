## 2. Phase 1 架构定案

**单通道：MCP 直接返回 `type: "image"` content block。两跳机制不建。**

- **OpenAI 生态的接入载体 = Codex CLI**，不是 ChatGPT 连接器，也不是 Codex 桌面版
- Codex CLI 甚至**不需要隧道**，直连 loopback HTTP 即可
- 桌面/聊天端若将来必须支持：要求模型**显式把 image 块转发进视觉输入**，并在产品侧对「未收到图片」做显式错误处理

1. **第 3 轮是真实感知，不是瞎猜。** 颜色与数量同时猜对只有 **1/18**，且她主动声明「直接看到了工具返回的图像像素，没有用代码解码」。
2. **我为修复「镜像混淆」埋的圆点锚点，在她身上没有生效。** 真值是 `/`（圆点应在方框**下部**），她答 `\`。说明**她读的是线的斜率，没有使用我给的判据锚点**。补救设计宣告失败（n=1，但方向明确）。

## 4. 与 CLI 的差异，以及它的含义

同一台机器、同一份配置、同一个模型（`gpt-6-luna`）、同一份服务端响应：

- **CLI：4/4 轮全对**
- **桌面版：3 轮里 2 轮连图像都没拿到，1 轮拿到且读错一项**

**结论：MCP 图片能否抵达视觉，取决于宿主 surface 的实现，而不是协议或服务端。** 这条差异是 Phase 0.4 存在的意义——不做这次测试，我们就会把产品建在「Codex 都能用」的假设上。

## 6. 三个客户端共同的优秀行为（产品该保住）

DSH、Codex CLI、Codex 桌面版、ChatGPT 聊天端，在收不到图像时**一律拒绝猜测**，并多次主动区分「送达」与「看见」：

> 「我确实收到并感知过 image 类型的数据块，但这不等于我保留了原始 PNG 字节，也不等于我现在能证明其完整性。」

**因此 Phase 1 契约第 7 条：工具与客户端必须显式上报「未收到图片」，禁止静默猜测。** 这条不是安全条款，是可用性条款——一个会编画面的视频理解产品比没有产品更糟。
