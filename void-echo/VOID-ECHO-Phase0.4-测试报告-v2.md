# VOID ECHO · Phase 0.4 测试报告 v2
## ChatGPT 能否看见经 Secure MCP Tunnel 传来的 MCP 原生图片

> **取代**：v1（`VOID-ECHO-Phase0.4-测试报告.md`）。v1 保留作历史与原始数据出处。
> **v2 的变化**：① 判据升级为**三重信号**，纯猜概率从 1/9 降到 **1/54**；② 判卷前先用程序**逐像素反解校准**，54 组全组合校验通过；③ 结论从「运气」更正为「两种假设并列」；④ 新增预注册判定阈值。

## 1. 测试装置

**服务端**：本地 MCP Echo Server，Streamable HTTP，`http://127.0.0.1:8765/mcp`，无鉴权，只听 loopback。
**暴露方式**：OpenAI Secure MCP Tunnel（`tunnel-client` v0.0.21，`tunnel_id = tunnel_6b09…（已脱敏，见本机 profile）`）。
**链路状态**：daemon `ready=True`，`dispatcher completed=20`，`failures=2`（两次均为 `unsupported channel "harpoon"`，与主通道无关）。

### 1.1 三重信号（`frame(n=1, secret=-1)`）

服务端**当场随机抽取**三个值，**只写入本机日志**，任何 text block 都不提及：

| 信号 | 位置 | 取值 | 状态数 |
|---|---|---|---|
| 粗竖条**数量** | 右上角 | 1 / 2 / 3 | 3 |
| 粗竖条**颜色** | 右上角 | teal / orange / purple / pink / lime / sky | 6 |
| **斜线方向** | 底部中央小面板 | `\` (backslash) / `/` (slash) / `-` (horizontal) | 3 |

**纯猜全对概率 = 1 / (3×6×3) = 1/54 ≈ 1.85%。**

基础场景恒为：浅底 `(245,245,250)` + 红椭圆 + 蓝方块。左上角深色条数量 = 帧序号，**该值写在文字里，只作锚点，不算证据**。

### 1.2 尺子校准（判卷前完成，非事后补做）

新增 `scripts/verify_pixels.py`：解码 PNG → 数右上角色段 → 反查调色板众数 → 用三条候选线段的暗像素占比判斜线方向。

```
54 组全组合（1/2/3 × 6 色 × 3 方向）逐像素反解：✅ 全部与渲染参数一致
端到端实测：像素反解 (3, teal, horizontal, 置信度1.0) == 日志真值 secret=3 colour=teal slash=horizontal
客户端回归：14/14 通过
```

> 这条流程是今天用三次误判换来的：**先校准量具，再打分。**

## 2. 已发生的历史数据（v1 全量，仍有效）

| 轮次 | 时刻 | 日志真值 | 实际像素 | 她的回答 | 归类 |

## 3. 两种假设（v1 的「运气」结论已撤回）

| | 内容 | 需要相信 | 与其余证据的关系 |
|---|---|---|---|
| **H1 间歇送达** | A 轮图片真进了视觉，其余轮次没进 | 同一条链路时好时坏 | 与「7 次否认」不矛盾——否认正是没送达时的正确表现 |
| **H2 A 轮虚构** | 图片从未送达 | ≈10% 巧合 **+ 她会谎称看见 PNG** | 与她 7 次拒绝猜测、并主动定位故障层的行为**相互矛盾** |

**当前倾向 H1，但无法自行判定。** 判别只能靠新证据——见第 4 节。

## 4. 新协议：三轮 × 三重信号，预注册阈值

**操作规范**：**一次调用 = 一个全新对话**，每轮只调 `frame(n=1, secret=-1)` 一次，不重试。（A 轮与 D–H 轮的样本瑕疵都出在「同对话多次调用」，这次堵掉。）

**提问模板**（每轮原样粘贴）：

> 请用 `void_echo_test` 的 `frame` 工具调用一次，参数 `n = 1`、`secret = -1`，不要重试。
> 然后只回答四件事：
> 1. 你收到的 `content` 里**有没有 `type` 为 `image` 的内容块**？有几个块、`type` 分别是什么？
> 2. **右上角**粗竖条的**颜色**（teal / orange / purple / pink / lime / sky 六选一）
> 3. **右上角**粗竖条的**数量**（1、2 或 3）
> 4. **底部中央小方框里那条线是什么方向**（`\` 反斜杠 / `/` 正斜杠 / `-` 水平）
>
> 没收到可视图片就直接说「没有图片」，不要猜。宁可交白卷。

### 预注册判定（现在就写死，跑完不改口径）

| 结果 | 概率参照 | 结论 |
|---|---|---|
| **任一轮「声称收到 + 三项全对」** | 单轮纯猜 1/54；三轮至少一次 ≈ 5.4% | ✅ **H1 成立**：Code Mode 存在可用子路径 → 单通道保留为可选优化，值得继续查明何时生效 |
| 三轮全部「没有图片」 | — | ✅ **H2 之外的送达率 ≈ 0** → 两跳定案，A 轮永久存疑，不再折腾 |
| **声称收到但三项有错** | — | 🔴 **最有价值的结果**：存在「谎称看见」路径 → 产品必须强制「未收到图片」显式上报，且**A 轮按虚构处理** |
| 声称收到、部分对（如颜色对数量错） | 单项纯猜 1/6 或 1/3 | ⚠️ 需更多样本；按二项分布单独评估，不轻率定案 |

## 5. 已定案的部分（不依赖本次判别）

| 端 | 关键帧视觉 | 依据 |
|---|---|---|
| **DSH** | ✅ **单通道**：MCP 直接返回 `type: "image"` | 多次实测：模型正确数出像素标记；返回字节 sha256 与本地一致；协议协商 2026-07-28 |
| **OpenAI / ChatGPT 聊天端** | ⚠️ **不可依赖 → 默认两跳**：MCP 返回引用，客户端用 `input_image` / `function_call_output` content parts 二次送入 | 声称收到 1/8；Code Mode 把 `content` 数组展开成数字键对象、丢失 `type` |

**两端共同硬约束**：工具必须能**显式报告「未收到图片」**，禁止静默猜测。本轮测试已证明该行为可被模型遵守——**产品应当要求它，而不是奖励猜对。**

## 6. 请 ChatGPT 判断的问题

1. **A 轮那次「9 根」你怎么解释？** 是真收到了图片，还是声称看见却编的？——现在有了 1/54 的三重协议，你可以用行为回答，不必只靠回忆。
2. **你的 MCP 连接器是否只有 Code Mode 一条路？** `content` 数组被展开成数字键对象、`type` 丢失，这是 bug 还是设计？有没有办法保持类型？
3. **Codex 是否走不同的 MCP 客户端实现？** 同一条 tunnel 挂到 Codex，原生 image block 有没有可能直接进视觉？（同样不吃 API 额度。）
4. **两跳方案在你的产品/API 侧是否正规？** MCP 返回图片引用 → 客户端作为 `input_image` 传入下一轮，有官方 schema 依据吗？已知坑（大小上限、URL 过期、data URL 长度、CORS）有哪些？
5. **这套判据还有没有漏洞？** 服务端随机、三重信号、预注册阈值、逐像素反解校准。如果你认为「不看图」的模型仍可能骗过它，请指出怎么骗。

> 请只回答你能实际确认的部分，不确定的明说不确定。**这条你已经用七次「没有图片」证明你会遵守——请继续保持，那比答对值钱。**
