# VOID ECHO · Phase 0.4 ChatGPT 审阅反馈

> 审阅对象：Phase 0.4 测试报告 v2、ChatGPT 反馈与补充观察、PNG renderer、MCP server、像素校验脚本  
> 目的：整理当前证据、修正文档与实现之间的不一致，并提出下一步可观测性改进。  
> 范围：本文件是审阅意见，不代表已执行代码修改或新一轮实验。

## 1. 先修正文档中的六色命名不一致

目前代码侧的颜色定义为：

- `teal`
- `orange`
- `purple`
- `magenta`
- `yellow`
- `gray`

`png.py` 中的 `ACCENTS`、`server.py` 的工具描述，以及像素校验逻辑采用的是上述命名。但 Phase 0.4 v2 报告/提问模板及反馈文档中出现了另一组名称（例如 `pink / lime / sky`），与实际 renderer 不一致。

**建议：统一以 renderer 和 server 当前实际使用的六个名称为准**，将测试报告、反馈文档、提问模板、判卷说明及相关 README/prompt 全部同步为：

`teal / orange / purple / magenta / yellow / gray`

本项首先是文档一致性修正。除非后续审查发现代码本身另有问题，否则不要为了迁就旧文档而改动 renderer 的颜色定义。

## 2. 明确像素校验的证明范围

`verify_pixels.py` 对 54 种像素组合进行穷举校验，可用于验证 renderer 的编码规则与本地 decoder/判读逻辑是否一致。

它**不能单独证明**：
- 图片已从 MCP Server 成功穿过 Secure MCP Tunnel；
- 客户端收到的图片与服务端生成的图片逐字节一致；
- 图片 payload 已进入模型实际的视觉输入；
- 模型回答是基于该图片，而非其他上下文或偶然猜中。

报告应明确区分“本地 renderer/decoder 校准”与“端到端传输/视觉输入验证”。

另外，数量与颜色都编码在右上角同一组竖条中，方向编码在图片的另一个区域。它们是同一张图片内的多个判读信号，**不是三个彼此独立的传输通道**。可以把多项信号用于降低盲猜概率，但不要将其描述成独立链路的交叉验证。

## 3. 补齐端到端证据链

建议后续实验为每次请求建立可关联的记录，尽可能贯穿：

1. MCP Server 生成图片；
2. Secure MCP Tunnel 接收/转发请求；
3. MCP 客户端收到工具结果；
4. 客户端解析 content blocks；
5. 图片 payload 被组装进模型实际视觉输入；
6. 模型返回回答。

建议记录字段：

- 单次实验的 `run_id`；
- 可用时的 request/correlation ID，以及 Tunnel dispatcher 对应的完成状态；
- 服务端生成 PNG 的 SHA256；
- 客户端实际收到并解码的 PNG SHA256；
- MCP content block 的顺序、类型、mime type、字节长度及图片 hash；
- 最终视觉请求中是否确实包含 image payload，以及 payload 类型/尺寸等非敏感元数据；
- 模型回答及对应的 run ID。

**关键要求：** 仅记录图片 URL、base64 字符串存在与否，或模型/界面文字声称“看到了图片”，都不足以证明图片进入了实际视觉输入。应在能观测的客户端组装边界记录证据，并将其与同一 run ID 关联。

日志应遵循最小化原则：不要记录完整图像 base64、Cookie、访问令牌或其他敏感凭据。可记录 hash、长度、mime type、状态和脱敏后的关联 ID。

## 4. 对历史 A 轮保持未决

A 轮曾出现模型回答与当时最后一帧像素内容吻合的情况，但现有记录不足以重建当时模型实际收到的视觉输入。

因此：
- 不应将 A 轮追认为原生图片链路成功；
- 也不应仅凭后续轮次失败就断言 A 轮一定是虚构或纯猜测；
- 继续标记为“未决/证据不足”，直到出现可核验的原始输入或端到端日志。

界面中的思考文案、最终回答以及模型自述都只能作为观察记录，不能替代传输层和视觉输入层的原始证据。

## 5. 统计口径保持一致

单轮三项信号的组合空间为 54 种，若三项均匀随机且独立地盲猜，单轮全对概率为 (1/54)。

三轮独立尝试中至少一次全对的概率为：

`1 - (53/54)^3 ≈ 5.45%`

报告中应区分：
- 单轮全对；
- 多轮至少一次全对；
- 部分命中；
- 声称收到图片但回答错误；
- 明确未收到图片；
- 传输/输入层有原始证据确认的成功或失败。

不要在看到结果后临时改变“成功”阈值。若要分析部分命中，应单独报告，不与全对统计混为一谈。

## 6. 建议的处理顺序

1. 先统一六色命名，并检查报告、反馈文档、提问模板与代码描述是否一致。
2. 在实验文档中明确像素校验与端到端验证的边界。
3. 为下一轮实验设计 run ID、hash 和各层状态的关联日志。
4. 在证据链设计完成并经审阅后，再决定是否进行新的端到端实验。

## 7. 本次审阅的执行边界

本反馈只提出审阅意见与后续建议：

- 不修改现有 renderer、server 或测试脚本；
- 不安装依赖、不改变本机环境；
- 不启动新的实验轮次；
- 不把尚未验证的推断写成事实。

任何代码修改或新实验均应在单独确认范围和验收标准后进行。

---

**审阅结论：** 当前最优先的工作不是增加实验次数，而是先消除文档与实现之间的颜色命名偏差，并建立能区分“服务端生成、客户端收到、模型实际收到视觉输入”这几个阶段的端到端证据链。
